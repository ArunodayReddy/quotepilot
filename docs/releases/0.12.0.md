# v0.12.0 "CMS-driven content" — Release Notes

> The parent agent merges this into CHANGELOG.md. Do not duplicate there.

**Date:** 2026-10-09
**Type:** architecture — page copy moves from hardcoded components to CMS data

## The change

Every user-facing string on the home page, about page, header, and footer now
lives in versioned JSON content files — the CMS — and components render purely
from props. When a page loads, the server fetches its content via the CMS
loader and passes it down. Zero hardcoded copy remains in these components.

## What changed

### CMS data — `apps/web/data/content/*.json`
- **`site.json`**: brand (name, mark, home link), site-wide SEO meta
  (default title, title template, description), header (nav links, CTA,
  theme-toggle labels), footer (brand blurb, link columns, honesty bullets,
  legal disclaimer, bottom bar).
- **`home.json`**: SEO, hero (eyebrow, title + accent, subtitle, ZIP form
  labels/placeholder/CTA/hint/error, secondary CTAs, note), how-it-works
  (heading, sub, 3 steps), carriers section copy, FAQ (heading, sub, items —
  the carriers item carries `dynamic: "carriers"` plus a full static fallback
  and the sentence template for the live answer), final CTA, JSON-LD
  description.
- **`about.json`**: SEO, title, lead, and sections modeled as structured
  rich text — paragraphs are arrays of segments (`text` | `bold` |
  `link{label,href}`), plus bullet lists and an optional CTA. No invented
  markup language; the renderer maps segments to elements.

### Loader — `apps/web/src/lib/cms.ts` (server-only)
- `getSiteContent()` / `getHomeContent()` / `getAboutContent()`: read the
  JSON, deep-validate every field, return typed content. Malformed content
  throws a loud, path-precise error (`CMS content invalid: home.json.hero —
  expected an object`) — never a silent fallback, never a half-rendered page.
- Content dir resolves from `apps/web` cwd with a repo-root fallback, so
  `dev.sh`, `next dev`, `next build`, and `next start` all work.
- In-memory cache in production; re-read on every request in dev so content
  edits apply without a restart.
- The loader is the seam: the file backend can be replaced by a real CMS
  (Sanity/Contentful/API) later without touching any component.

### Components → presentational
- `app/page.tsx`: async server component — loads home content on page load,
  feeds `generateMetadata` (title/description from CMS) and FAQ JSON-LD
  (dynamic slots use their CMS fallback), passes content to `<Home/>`.
- `views/Home.tsx`: `Home({ content })` — hero, ZIP form, how-it-works,
  carrier marquee, FAQ, final CTA all render from props. The carrier marquee
  names and the carriers FAQ answer still come from the live registry API
  (already feed-driven); the FAQ sentence template is now CMS-owned too.
- `app/about/page.tsx` + `views/About.tsx`: same pattern; `generateMetadata`
  from CMS.
- `app/layout.tsx`: async — loads site content, passes to `<Header/>` and
  `<Footer/>`; site-wide metadata from `site.json` via `generateMetadata`.
- `components/Header.tsx` / `Footer.tsx`: render nav, CTAs, columns, legal
  copy from props.
- `lib/homeContent.ts`: FAQ_DEFS deleted (moved to `home.json`); keeps only
  the dynamic composition logic (`carriersAnswer` with a CMS-provided
  template, `buildJsonLd`, `staticFaqs`).

## Verification

- `tsc --noEmit` clean; `next build` green — 10/10 pages, `/` and `/about`
  prerendered with CMS content (prerender is the build-time gate: bad content
  fails the build).
- Prerendered HTML spot-checked: hero title, hero note, about section
  heading, and footer copyright all present from CMS data.
- Loader validation smoke-tested: malformed `home.json` throws
  `CMS content invalid: home.json.hero — expected an object`; file restored
  afterwards.

## Deliberately out of scope

- Other pages (wizard, quotes, agents, legal) keep their current copy for now —
  the pattern is proven on home/about/site and extends mechanically.
- No runtime content editing UI; content changes are JSON edits + deploy.
  A real CMS backend plugs into `lib/cms.ts` when needed.
- No new env vars, no new dependencies.
